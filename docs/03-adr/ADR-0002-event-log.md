# ADR-0002. Событийный журнал + проекции (гибридный подход)

**Статус:** Принято
**Дата:** 02.10.2026
**Заменяет:** —
**Заменён на:** —

---

## Контекст

ТЗ п. 7.1–7.3 требует:
- структура хранения должна расширяться и изменяться без потери накопленных данных;
- система не должна останавливаться на время изменений;
- должна быть возможность восстановить данные после сбоя;
- должна быть возможность связать событие, фото, документ и рейс независимо от раскладки файлов.

---

## Решение

Использовать **гибридный подход** с разделением данных на три категории:

| Категория | Примеры | Как хранится |
|---|---|---|
| **Факты рейса** | события, координаты, время, фото | `events` — append-only журнал |
| **Справочники** | users, orders, trips, cargo_units, checklist_templates | обычные таблицы с CRUD |
| **Проекции** | trip_timeline, trip_progress, trip_completeness | материализованные представления |

---

## Обоснование

- **Чистый event sourcing** — сложен, команда не вытянет за 2 месяца.
- **Простые state-таблицы** — не выдержат грандиозных обновлений модели (например, второй тип груза с другой иерархией точек).
- **Гибрид** даёт 80% пользы за 20% усилий.

---

## Последствия

- События нельзя `UPDATE` после `state='accepted'`. Исправление = новая запись + `corrects_event_id`.
- Смена логики проекции = пересборка из `events`, старые данные не трогаются.
- Новые поля в `payload_jsonb` пишутся без переписывания старых записей.
- Старые события остаются валидными при изменении схемы (через `payload_schema_version`).

---

## Влияние на обновляемость

**Не требует релиза APK/IPA:**
- Изменение логики проекций.
- Пересборка проекций.
- Добавление новых полей в `payload_jsonb` (серверная часть).
- Изменение правил чтения.

**Требует релиза APK/IPA:**
- Если клиент должен **отправлять** новые поля в `payload_jsonb`.
- Если клиент должен **читать** новые поля из проекций.

**Правило:** сервер может писать новые поля без релиза APK/IPA. Клиент может читать новые поля только после релиза.
