## Контекст

ТЗ п. 4.1 требует:
- все действия логируются.

ТЗ п. 4.3 требует:
- `@reiscontrol_devbot` — разработчику: логи (успех/ошибка/краш).

ТЗ п. 13 (критерии приёмки):
- разработчик получает логи в Telegram.

ТЗ п. 6.4 требует:
- тестировать изменения до выпуска в продуктив;
- откатить неудачное обновление;
- среда для проверки и порядок выпуска.

ТЗ п. 15 (ожидаемый результат):
- снижено время на закрытие рейсов;
- система готова к развитию.

Система распределённая: Android, iOS, API, воркеры, scheduler, боты. Без единой системы логирования отладка и мониторинг невозможны.

---

## Решение

### 1. Формат логов

**Только структурированные JSON-логи.** Никаких `print(...)` и `console.log(...)`.

**Обязательные поля каждого лога:**

| Поле | Описание |
|---|---|
| `timestamp` | ISO 8601, UTC |
| `level` | `debug` / `info` / `warning` / `error` / `critical` |
| `service` | `api` / `worker` / `scheduler` / `android` / `ios` / `web` / `telegram` |
| `message` | Человекочитаемое сообщение |
| `trace_id` | Уникальный ID для трассировки одного запроса/события |
| `user_id` | ID пользователя (если применимо) |
| `device_id` | ID устройства (если применимо) |
| `trip_id` | ID рейса (если применимо) |
| `event_id` | ID события (если применимо) |
| `app_version` | Версия приложения |
| `platform` | `android` / `ios` (если применимо) |
| `context` | Дополнительные поля (объект) |

**Пример:**

```json
{
  "timestamp": "2026-10-01T14:20:33.123Z",
  "level": "info",
  "service": "api",
  "message": "Event accepted",
  "trace_id": "tr_01HX...",
  "user_id": "usr_01HX...",
  "device_id": "dev_01HX...",
  "trip_id": "trip_01HX...",
  "event_id": "evt_01HX...",
  "app_version": "1.0.0",
  "platform": "android",
  "context": {
    "event_type_code": "LOADING",
    "attachments_count": 12,
    "duration_ms": 245
  }
}
```

### 2. Уровни логирования

| Уровень | Когда использовать | Куда идёт |
|---|---|---|
| `debug` | Детали для отладки (только в dev/staging) | Локальный файл, не в prod |
| `info` | Успешные операции | Централизованное хранилище |
| `warning` | Что-то не так, но не критично | Централизованное хранилище + dev-bot (дайджест раз в час) |
| `error` | Ошибка, требует внимания | Централизованное хранилище + dev-bot (сразу) |
| `critical` | Критическая ошибка | Централизованное хранилище + dev-bot (сразу) + алерт |

**Правило:** в prod не логируем `debug`. Уровень регулируется переменной окружения.

### 3. Что логируем обязательно

**На сервере:**
- Все входящие запросы API (метод, путь, статус, длительность, `trace_id`).
- Все ошибки API (с `trace_id` и стеком).
- Все операции с событиями.
- Все операции с вложениями.
- Все операции с конфигурацией.
- Все операции с токенами.
- Все операции с правами.
- Все операции с рейсами.
- Работу воркеров.
- Работу scheduler.
- Отправку уведомлений.

**На клиенте (Android / iOS):**
- **Только ошибки и сбои** (камера, GPS, сеть).
- **Обычные действия не логируем** (по решению заказчика).
- Краши приложения.
- Ошибки загрузки файлов.
- Ошибки синхронизации.

**На веб-кабинете:**
- Вход и выход.
- Создание заявки.
- Публикация конфигурации.
- Подтверждение закрытия рейса.
- Изменение прав.
- Ошибки API.

**В Telegram-ботах:**
- Отправка уведомления (успех, ошибка).
- Ошибки Bot API.

### 4. Что НЕ логируем

- **Пароли** (даже хеши).
- **Access-токены и refresh-токены** (только `user_id`).
- **Полные ПДн** (ФИО, номер ВУ, телефон — только `user_id`).
- **Координаты** без необходимости.
- **Содержимое фото** (только метаданные: размер, `sha256`).
- **Секреты** (ключи, пароли БД).
- **Полные payload запросов** (только ключевые поля).

**Правило:** логи не должны содержать данные, утечка которых навредит. См. ADR-0010.

### 5. Централизованное хранилище

**Решение:** **Yandex Cloud Logging**.

- Все сервисы пишут логи в единое хранилище.
- Логи структурированы (JSON).
- Поиск по `trace_id`, `trip_id`, `event_id`, `user_id`.
- Хранение: **1 год** (горячее — 30 дней, холодное — 11 месяцев).
- Доступ: **только разработчикам**.

### 6. Dev-bot (`@reiscontrol_devbot`)

**Назначение:** оперативное оповещение разработчика.

**Что отправляется:**

| Уровень | Как отправляется |
|---|---|
| `error` | Сразу, с контекстом |
| `critical` | Сразу, с контекстом + @mention |
| `warning` | Агрегированно раз в час (дайджест) |
| `info` | Не отправляется |
| `debug` | Не отправляется |

**Формат сообщения:**

```
🔴 ERROR
Сервис: api
Время: 2026-10-01 14:20:33 UTC
Trace: tr_01HX...
Сообщение: Event rejected
Контекст: event_type=LOADING, reason=config_version_mismatch
```

**Rate limiting:** не более 20 сообщений в минуту. При превышении — агрегация.

**Кому:** только разработчикам. Не логистам. Не заказчику.

**Отдельный канал для алертов:** не используется. Всё идёт в dev-bot.

### 7. Логирование на клиенте (Android / iOS)

- **Локальный файл** (rolling, максимум 10 МБ).
- **Отправка на сервер:**
  - `error` и `critical` — сразу, через `POST /logs`.
  - `info` — батчами раз в час.
  - `debug` — только в dev-сборке.
- **Краши** — через dev-bot.
- **Не отправляем:** содержимое фото, полные ПДн, токены.

### 8. Trace ID

- **Генерация:** на клиенте при создании события (`trace_id` = `client_event_id`).
- **Передача:** в заголовке `X-Trace-Id` во всех запросах.
- **Использование:** во всех логах, связанных с этим событием.
- **Цель:** связать логи клиента, API, воркеров и БД для одного события.

### 9. Логирование в офлайне

- На клиенте логи копятся локально.
- При появлении сети — отправляются на сервер (батчами).
- **Не теряются** при краше.
- **Не блокируют** работу приложения.

### 10. Мониторинг и алерты

**Метрики:**
- Количество событий в час.
- Количество ошибок API в час.
- Среднее время ответа API.
- Количество застрявших outbox (более 24 ч).
- Количество рейсов в статусе `pending_logistician` (более 7 дней).
- Объём Object Storage.
- Количество активных устройств.

**Алерты:**
- Резкий рост ошибок (`error` > N в минуту).
- API недоступен.
- PostgreSQL недоступен.
- Object Storage недоступен.
- Застрявшие outbox.
- Аномалии GPS.
- Расхождение часов (`clock_skew_ms` > порог).

## Обоснование

- Структурированные JSON-логи — стандарт, легко парсить и искать.
- Единое хранилище — обязательно для распределённой системы.
- Dev-bot — оперативное оповещение, требование ТЗ.
- Trace ID — связывает все логи одного события.
- Отсутствие ПДн в логах — требование 152-ФЗ (см. ADR-0010).
- Локальные логи на клиенте — требование офлайн-first (см. ADR-0004).
- Логирование только ошибок на клиенте — решение заказчика (не засорять логи).

## Последствия

- Появляется **единый формат логов** для всех сервисов.
- Появляется **trace_id** во всех запросах и логах.
- Появляется **dev-bot** с rate limiting.
- Появляется **централизованное хранилище** логов (Yandex Cloud Logging).
- Логи **не содержат** ПДн и секретов.
- Логи **не теряются** при краше клиента.
- Появляются **метрики и алерты**.

---

## Влияние на обновляемость

**Не требует релиза APK/IPA:**
- Изменение формата логов на сервере.
- Изменение уровней логирования.
- Изменение dev-bot.
- Изменение централизованного хранилища.
- Изменение метрик и алертов.
- Изменение сроков хранения логов.

**Требует релиза APK/IPA:**
- Изменение формата логов на клиенте.
- Изменение состава того, что логируется на клиенте.
- Изменение способа отправки логов на сервер.
- Изменение trace_id на клиенте.

**Правило:** логирование на сервере — без релиза. Логирование на клиенте — с релизом.

## Открытые вопросы

1. Где хранить логи?
   **Ответ:** Yandex Cloud Logging.

2. Срок хранения логов?
   **Ответ:** 1 год.

3. Что логировать на клиенте?
   **Ответ:** Только ошибки и сбои. Обычные действия не логируем.

4. Нужен ли Crashlytics?
   **Ответ:** Нет. Только dev-bot.

5. Кому доступны логи?
   **Ответ:** Только разработчикам.

6. Нужен ли отдельный канал для алертов?
   **Ответ:** Нет, используем dev-bot.

7. Как агрегировать warning?
   **Ответ:** Раз в час.

8. Нужны ли метрики в Grafana?
   **Ответ:** Нет, достаточно дашборда в Yandex Cloud.
