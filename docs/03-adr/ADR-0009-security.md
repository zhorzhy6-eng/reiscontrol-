# ADR-0009. Безопасность: аутентификация, авторизация, аудит

**Статус:** Принято
**Дата:** 02.10.2026
**Заменяет:** —
**Заменён на:** —

## Контекст

ТЗ п. 4.1 требует:
- вход по телефону и паролю;
- список заявок — только свои.

ТЗ п. 7.2 требует:
- разграничение доступа к данным по ролям и по рейсам.

ТЗ п. 6.4 требует:
- код должен быть понятен и сопровождаем силами команды, не участвовавшей в разработке.

ТЗ п. 17 требует:
- исключительные права на код — заказчику;
- аккаунты облака, домена, ботов — на заказчика.

Система работает с персональными данными водителей (геолокация, ФИО, номер ВУ) и коммерческими данными заказчика (рейсы, клиенты, фото грузов). Утечка или несанкционированный доступ — репутационный и юридический риск.

---

## Решение

### 1. Аутентификация

- **Access-токен (JWT):** срок жизни **15 минут**. Подписывается HS256, секрет — в Yandex Lockbox.
- **Refresh-токен:** срок жизни **30 дней**. Хранится в БД в виде хеша (`refresh_tokens.token_hash`). Отзывается при выходе и при смене пароля.
- **Пароли:** bcrypt или argon2id. Никакого хранения в открытом виде.
- **Привязка к устройству:** refresh-токен привязан к `device_id`. При входе с нового устройства — старое остаётся активным до истечения срока или до явного отзыва.
- **Заголовки запросов:** `Authorization: Bearer <access_token>`, `X-App-Version`, `X-Platform`, `X-Device-Id`.

### 2. Авторизация

- **RBAC:** роли `driver`, `logistician`, `admin`. У каждой роли — свой набор прав.
- **Скопы по рейсам:** таблица `access_scopes` связывает пользователя с областью (`client`, `trip`, `region`).
- **Проверка на каждом запросе:** пользователь имеет доступ к рейсу только если он:
  - участник рейса (`trip_participants`), **или**
  - логист с соответствующим скопом, **или**
  - админ.
- **Логист видит только своих клиентов** (настроено через `access_scopes`).
- **Водитель видит только свои рейсы.**

### 3. Аудит

- **Все действия логиста** пишутся в `audit_log`: кто, что, когда, над каким объектом.
- **Все действия админа** — аналогично.
- **Действия водителя** фиксируются как события рейса (append-only журнал).
- **Аудит неизменяем:** запись в `audit_log` нельзя удалить или изменить (только добавление).
- **Доступ к аудиту:** только админ.

### 4. Транспорт

- **HTTPS обязателен** для всех эндпоинтов, кроме health-check.
- **HSTS** включён.
- **Сертификаты** — Let's Encrypt или Yandex Certificate Manager, автопродление.
- **CORS** — только для веб-кабинета, whitelist доменов.

### 5. Хранение секретов

- **Yandex Lockbox** для всех секретов: JWT-секрет, пароли БД, ключи Object Storage, токены Telegram-ботов.
- **Никаких секретов в коде, в git, в APK/IPA.**
- **Ключи Object Storage** — только presigned URL на клиенте. Прямые ключи в APK/IPA запрещены.

### 6. Мобильное приложение

- **EncryptedSharedPreferences** (Android) / **Keychain** (iOS) для refresh-токена.
- **PIN** для повторного входа. Биометрия — не используется.
- **Обфускация APK/IPA** (R8/ProGuard, Swift Shielding) в релизной сборке.
- **Проверка подписи APK/IPA** при обновлении (см. ADR-0008).
- **Certificate pinning** — не используется на старте. Отложен до RuStore.

### 7. Защита API

- **Rate limiting** на эндпоинты авторизации (защита от брутфорса).
- **Idempotency-Key** для всех операций, создающих данные (см. ADR-0004).
- **Валидация всех входных данных** через Pydantic-схемы.
- **Ограничение размера payload** (кроме presigned URL).
- **Логирование всех 401/403** в dev-bot для алертов.

### 8. Права и передача

- **Исключительные права на код** — заказчику (ТЗ п. 17).
- **Аккаунты Yandex Cloud, домена, Telegram-ботов** — на заказчика.
- **Передача:** репозиторий, доступы к облаку, документация, инструкции.

## Обоснование

- JWT + refresh — стандарт индустрии, легко реализуется, поддерживается всеми библиотеками.
- RBAC + `access_scopes` — прямое закрытие п. 7.2 ТЗ.
- `audit_log` — требование доказательности и разграничения доступа.
- Lockbox — безопасное хранение секретов без риска утечки через код.
- EncryptedSharedPreferences / Keychain — защита токенов при потере телефона.
- PIN вместо биометрии — проще, работает на всех устройствах, не требует дополнительных разрешений.

## Последствия

- Появляется таблица `refresh_tokens` с отзывом.
- Появляется таблица `audit_log` (append-only).
- Появляется таблица `access_scopes`.
- Все эндпоинты, кроме `/auth/login` и `/health`, требуют Bearer-токен.
- При смене пароля все refresh-токены пользователя отзываются.
- Логист не может видеть чужие рейсы.
- Водитель не может видеть чужие заявки.
- Все действия логиста и админа — в аудите.
- Аудит доступен только админу.

---

## Влияние на обновляемость

**Не требует релиза APK/IPA:**
- Изменение политики паролей на сервере.
- Изменение сроков жизни токенов.
- Изменение правил RBAC.
- Добавление новых ролей.
- Изменение аудита.
- Ротация секретов в Lockbox.

**Требует релиза APK/IPA:**
- Изменение формата JWT (структура claims).
- Изменение способа хранения токенов на клиенте.
- Добавление certificate pinning.
- Изменение логики refresh на клиенте.
- Изменение способа входа (PIN → биометрия).

**Правило:** безопасность на сервере — без релиза. Безопасность на клиенте — с релизом.

## Открытые вопросы

1. Нужна ли **биометрия** для повторного входа?
   **Ответ:** Нет, достаточно PIN.

2. Нужен ли **certificate pinning** на старте?
   **Ответ:** Нет. Отложить до RuStore.

3. Сколько **логистов** и нужны ли им разные скопы по клиентам?
   **Ответ:** 2–3 логиста. Скопы по клиентам нужны.
   Логист видит только своих клиентов. Админ — всех.

4. Нужно ли **принудительное завершение сессии** при смене пароля администратором?
   **Ответ:** Да, нужно.

5. Нужно ли **логировать действия водителя** отдельно от событий рейса?
   **Ответ:** Да, но только ошибки и сбои (камера, GPS, сеть).
   Обычные действия не логируем.

6. Нужна ли **обфускация APK/IPA**?
   **Ответ:** Да.
