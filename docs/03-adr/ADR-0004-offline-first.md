# ADR-0004. Офлайн-first синхронизация с идемпотентностью

**Статус:** Принято
**Дата:** 02.10.2026
**Заменяет:** —
**Заменён на:** —

---

## Контекст

ТЗ п. 4.1, 5.2, 5.3:
- работа без интернета;
- события копятся локально;
- отправка при появлении сети;
- статус «В очереди» / «Отправлено»;
- стабильная работа без перезапуска;
- прогресс не теряется.

Рейсы длятся неделями, сеть может отсутствовать днями.

ТЗ п. 4.1 также требует: **«До завершения фотосъёмки событие не сохраняется»**.

---

## Решение

- **Клиент — источник истины для фактов.** Каждое событие получает `client_event_id` (UUIDv7) **до** отправки.
- **Жизненный цикл события:**

  | Состояние | Где происходит | Что означает | Что видит водитель |
  |---|---|---|---|
  | `draft` | телефон | черновик, шаги чек-листа не выполнены | «Не закончено» |
  | `complete` | телефон | все обязательные шаги выполнены, закрыто локально | «Готово к отправке» |
  | `queued` | телефон | в очереди отправки (`outbox`), ждёт сеть | «В очереди» |
  | `uploaded` | телефон → сервер | метаданные и файлы загружены | «Отправлено» |
  | `accepted` | сервер | принято и спроецировано | «Принято» |
  | `rejected` | сервер | отклонено, водителю приходит причина | «Ошибка, обратитесь к логисту» |

  Переходы: `draft → complete → queued → uploaded → accepted / rejected`.
  Из `rejected` возможен возврат в `draft` для исправления.

- **Локальный outbox** (Room + WorkManager) с ретраями.
- **Уникальный индекс** `(client_event_id, device_id)` на сервере — защита от дублей.
- **Двухфазная загрузка файлов** через presigned URL.
- **Локальные файлы удаляются** только после `state='accepted'` на сервере.
- **Требование «событие не сохраняется до окончания съёмки»** выполняется на уровне `complete`: незавершённый черновик виден водителю как «Не закончено», логисту не уходит.

---

## Обоснование

- Без идемпотентности повторная отправка создаст дубли.
- Без outbox краш приложения = потеря рейса.
- Двухфазная загрузка снимает с API гигабайты трафика.
- Статусная модель защищает от потери при сбое: черновик восстанавливается с диска.
- Статусная модель закрывает требование ТЗ п. 4.1 «до завершения фотосъёмки событие не сохраняется» без риска потери данных.

---

## Последствия

- Офлайн-ядро закладывается **на этапе 1**, а не этапом 4 (как в ТЗ v3.0). См. ТЗ v4.0.
- Все операции с событиями идемпотентны.
- Появляется UI статусов «В очереди» / «Отправлено» / «Ошибка».
- Приоритеты загрузки: сначала превью и метаданные, потом оригиналы.
- При сбое (краш, севшая батарея) черновик восстанавливается с диска при следующем запуске.

---

## Влияние на обновляемость

**Не требует релиза APK/IPA:**
- Изменение политики ретраев на сервере.
- Изменение приоритетов загрузки на сервере.
- Изменение логики приёма (если формат события не меняется).

**Требует релиза APK/IPA:**
- Изменение формата `client_event_id`.
- Изменение статусной модели события.
- Изменение логики outbox на клиенте.
- Новые поля в событии, которые клиент должен заполнять.

**Правило:** клиент — источник истины для фактов. Любое изменение того, что клиент отправляет, требует релиза APK/IPA.
