# ADR-0008. Версионирование, миграции expand/contract и обновление приложения

**Статус:** Принято
**Дата:** 02.10.2026
**Заменяет:** —
**Заменён на:** —

---

## Контекст

ТЗ п. 6.2 требует:
- обновления приложения **не должны требовать одновременного обновления всех водителей**;
- старые версии приложения должны продолжать работать с сервером в течение согласованного периода;
- должна быть возможность поэтапного включения новых функций;
- должна быть возможность отключить новую функцию без выпуска нового релиза.

ТЗ п. 6.3 требует:
- серверная часть должна поддерживать **несколько версий мобильного приложения** одновременно;
- изменения в форматах данных **не должны ломать уже сохранённые рейсы**;
- должна быть предусмотрена политика **минимальной поддерживаемой версии**;
- принудительное обновление — только в крайних случаях и с обоснованием.

ТЗ п. 14: распространение через **APK напрямую**, позже — **RuStore**. Обновление без потери данных и без остановки работы.

**Дополнительно (решение заказчика от 02.10.2026):**
- Android — основной клиент на старте.
- iOS — закладывается сразу, реализуется позже.
- RuStore — канал обновления для Android.

## Решение

### Независимые версии

| Что | Где хранится |
|---|---|
| App version | `X-App-Version` заголовок |
| Platform | `X-Platform` заголовок (`android` / `ios`) |
| API version | URL `/api/v1`, `/api/v2` |
| Config version | `config_snapshots` на рейс |
| Event schema version | `payload_schema_version` |
| DB schema version | Alembic |

### Правила API

- Только **аддитивные** изменения.
- Удаление поля = депрекация на 2 релиза → отключение флагом → удаление через полгода.
- Каждое сообщение несёт `schema_version`.
- API не привязан к платформе — Android и iOS используют одни эндпоинты.

### Правила миграций БД

Только **expand/contract**:
1. Добавили поле.
2. Пишем в оба.
3. Бэкфил.
4. Переключили чтение.
5. Удалили старое.

Никогда «big bang» миграция со стопом.

### Правила обновления APK/IPA

**Каналы обновления:**

| Платформа | Канал | Метод |
|---|---|---|
| Android | Direct APK | Свой канал (Object Storage), проверка SHA-256 и подписи |
| Android | RuStore | Публикация в RuStore (позже) |
| iOS | TestFlight | Для пилота (позже) |
| iOS | App Store / Enterprise | Для production (позже) |

**Таблица `app_releases`:**

| Поле | Тип | Назначение |
|---|---|---|
| `version_code` | int | Код версии |
| `version_name` | text | Имя версии |
| `platform` | text | `android` / `ios` |
| `channel` | text | `direct` / `rustore` / `testflight` / `appstore` / `enterprise` |
| `min_supported` | int | Минимальная поддерживаемая версия |
| `rollout_percent` | int | Процент раскатки |
| `apk_url` | text | URL файла (для direct) |
| `sha256` | text | Хеш файла |
| `released_at` | timestamptz | Дата релиза |

**Правила:**
- Обновление **не принудительное**, кроме случая `min_version`.
- Ответ `426 Upgrade Required` — только в исключительных случаях, с обоснованием в ADR.
- Для Android: `GET /app/releases/latest?platform=android&channel=direct`.
- Для iOS: `GET /app/releases/latest?platform=ios&channel=testflight`.

### Правила совместимости

- Старые версии приложения **должны уметь выгрузить** накопленные материалы (многодневные рейсы).
- Проекция конфига под версию клиента: сервер фильтрует элементы по `min_app_version`.
- Неизвестный примитив на клиенте → **мягкая деградация**, никогда краш.
- Android и iOS используют **один API**, но разные каналы обновления.

## Обоснование

- Рейсы длятся неделями, старая версия должна работать.
- Expand/contract позволяет откатить неудачное обновление без потери данных.
- Свой канал APK необходим для Huawei без Google Play (ТЗ п. 4.1, 5.5).
- RuStore — по решению заказчика.
- iOS — закладывается сразу, чтобы не переделывать API и схему БД.

---

## Последствия

- Появляется **контракт-first**: `openapi.yaml` — источник правды.
- Contract-тесты в CI обязательны.
- ADR на каждое принудительное обновление — обязателен.
- Feature flags позволяют включать/отключать функции без релиза.
- `app_releases` содержит `platform` и `channel` — готово к iOS и RuStore.

## Влияние на обновляемость

**Не требует релиза APK/IPA:**
- Изменение конфигурации (см. ADR-0003).
- Изменение правил завершения.
- Изменение шаблонов уведомлений.
- Отключение функции через `feature_flags`.
- Изменение `min_supported` (для новых установок).
- Изменение `rollout%`.
- Изменение `channel` (переключение между direct и rustore).

**Требует релиза APK/IPA:**
- Новая страница (экран).
- Новый примитив.
- Изменение UI главного экрана.
- Новая навигация.
- Новый клиентский адаптер.
- Изменение клиент-серверного контракта в сторону, где клиент должен отправлять новые данные.
- Реализация iOS-клиента.

**Правило:** если изменение затрагивает **код на клиенте** — нужен релиз. Если только **данные** — без релиза.

## Открытые вопросы

1. Какой срок поддержки старых версий?
   **Ответ:** 3 месяца.

2. Когда планируется публикация в RuStore?
   **Ответ:** После пилота Android.

3. Когда планируется iOS?
   **Ответ:** После стабилизации Android. Срок — не определён.
