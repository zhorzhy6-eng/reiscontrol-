# ADR-0012. Партиционирование отложено до этапа масштабирования

**Статус:** принято 03.10.2026  
**Контекст:** этап 1, walking skeleton  
**Связанные решения:** ADR-0002, ADR-0004, ADR-0008

## Контекст

Схема БД v1.1 предлагает месячное партиционирование `events` по `created_at`
и `location_tracks` по `recorded_at`. При этом для `events` требуется
глобальная уникальность `(client_event_id, device_id)` для идемпотентности.
PostgreSQL 16 не обеспечивает такой `UNIQUE` на партиционированной по
`created_at` таблице без добавления ключа партиционирования в ограничение.
Добавление `created_at` ослабило бы защиту от повторной отправки.

## Решение

- На этапе 1 `events` — обычная таблица с `UNIQUE (client_event_id, device_id)`.
- На этапе 1 `location_tracks` — обычная таблица с индексами для выборки по
  устройству, рейсу и времени.
- Партиционирование обеих таблиц рассматривается после роста журнала свыше
  **1 млн событий**. Это отдельная миграция по схеме expand/contract:
  новая структура → параллельная запись и бэкфил → сверка → переключение
  чтения → удаление старой структуры после периода совместимости.
- До переключения нужно отдельно спроектировать глобальную защиту
  `(client_event_id, device_id)` и проверить её под конкурентной нагрузкой.

## Последствия

Идемпотентность этапа 1 обеспечивается прямым ограничением PostgreSQL.
Первая миграция не создаёт партиции и не выполняет массовое перемещение
данных. Решение о будущем партиционировании не меняет контракт API и
формат клиентских событий.
