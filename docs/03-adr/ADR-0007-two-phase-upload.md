# ADR-0007. Двухфазная загрузка файлов через presigned URL

**Статус:** Принято
**Дата:** 02.10.2026
**Заменяет:** —
**Заменён на:** —

---

## Контекст

ТЗ п. 4.1: 12 ракурсов × 8 машин + документы ≈ **110–130 фото на рейс**.
30 рейсов/мес → **~2 ГБ/мес**.
Плохая связь, нужна докачка.
ТЗ п. 5.2: событие сохраняется локально, отправка при появлении сети.

---

## Решение

Загрузка в **3 шага**:

1. `POST /v1/attachments:init` → `attachment_id` + presigned PUT URL.
2. Клиент льёт файл **напрямую в Object Storage** (с докачкой).
3. `POST /v1/attachments/{id}:commit` с `sha256`, размером, метаданными водяного знака.

---

## Обоснование

- Снимает с API гигабайты трафика.
- Убирает лимиты payload.
- Позволяет докачку в плохой связи.
- API отвечает за 3 секунды и не занимается файлами.
- `sha256` даёт возможность проверить целостность (п. 7.3 ТЗ).

---

## Последствия

- API становится stateless и легко масштабируется.
- Появляется `sha256` для проверки целостности.
- Тяжёлое (превью, водяные знаки) — в воркерах.
- Ключ объекта в Object Storage — **иммутабельный**. Меняете правила раскладки — новые файлы пишутся по-новому, старые остаются на месте, связь через `attachment_id` не рвётся (п. 7.2 ТЗ).

---

## Влияние на обновляемость

**Не требует релиза APK:**
- Изменение правил раскладки в Object Storage.
- Изменение политики lifecycle (холодное хранилище).
- Изменение способа генерации превью на сервере.
- Изменение логики `:commit` на сервере.

**Требует релиза APK:**
- Изменение формата `:init` / `:commit`.
- Изменение способа получения `sha256` на клиенте.
- Изменение логики докачки на клиенте.
- Новые типы вложений, которые клиент должен создавать.

**Правило:** двухфазная загрузка — часть клиент-серверного контракта. Изменения формата требуют релиза APK.
